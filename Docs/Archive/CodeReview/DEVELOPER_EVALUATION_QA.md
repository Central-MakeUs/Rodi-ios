# 개발자 평가 예상 질문·답변

> 2026-09-05에 보존한 과거 발표 자료다. 아래의 현재 코드·활성 문서 표현은 작성 당시 기준이며, 현재 구현 계약이나 AI 작업 지침으로 사용하지 않는다.

## 목적

이 문서는 RODI의 코드리뷰, 기술 면접, 프로젝트 발표에서 개발자가 물을 수 있는 질문에 답하기 위한 내부 준비 자료다. 답변은 현재 코드와 활성 문서를 기준으로 하며, 실기기 확인이 필요한 항목은 완료처럼 표현하지 않는다.

## 답변 원칙

- 첫 문장에서 결론을 말한다.
- 이어서 선택 이유와 구현 근거를 짧게 설명한다.
- 검증하지 않은 실기기·서버·외부 앱 동작은 한계로 명확히 말한다.

## 부스 방문자용 구현 심화 질문

개발 경험이 있는 방문자가 구현 방식을 궁금해할 때 사용하는 답변이다. 폴더 구조나 상태 관리 패턴 이름보다, 입력·위치·서버 응답이 실제 화면과 기록으로 이어지는 과정을 설명한다.

### 구현 1. SwiftUI 화면에 지도는 어떻게 넣었나요?

**SwiftUI 화면 안에 Kakao 지도 UIKit View를 연결하는 방식으로 넣었습니다.** 지도 엔진이 준비되면 카메라·마커·경로 선을 전달하고, marker 탭·지도 이동 같은 지도 이벤트는 다시 앱 화면의 선택 상태로 전달합니다.

### 구현 2. 지도 중앙을 움직일 때 주소는 어떻게 알아내나요?

**지도 중앙 좌표가 바뀐 뒤 잠시 기다렸다가 주소 변환 요청을 보냅니다.** 드래그 중 모든 좌표를 요청하지 않고 마지막 위치만 조회하며, 이전 주소는 새 주소 응답이 올 때까지 유지해 화면이 깜빡이지 않게 했습니다.

### 구현 3. 지도를 움직인 뒤 추천 목록은 어떻게 새로 불러오나요?

**현재 지도 범위를 서버 요청 값으로 바꿔 목록을 다시 받습니다.** 사용자가 빠르게 여러 지역을 이동할 수 있어 요청마다 순번을 두고, 가장 마지막 지도 범위의 결과만 목록에 반영합니다.

### 구현 4. 마커를 수백 개 그릴 때 멈춤은 어떻게 줄였나요?

**처음 보이는 marker를 먼저 그리고 나머지는 작은 묶음으로 나눠 추가합니다.** 첫 화면은 빠르게 보이게 하고, 추가 marker는 짧은 간격으로 이어 그려 화면을 오래 멈추지 않게 했습니다.

### 구현 5. 확대 수준에 따라 marker가 바뀌는 것은 어떻게 구현했나요?

**같은 장소 목록을 지도 확대 수준에 맞는 지역 단위로 묶어 다른 marker 모델로 바꿉니다.** 멀리서는 숫자 cluster, 가까워지면 개별 코스·주차장 marker를 보여 주며 한 곳만 남은 cluster는 바로 단일 marker로 바꿉니다.

### 구현 6. 검색 결과를 눌렀을 때 지도와 바텀시트가 함께 바뀌는 이유는 무엇인가요?

**선택한 장소의 ID를 공통 선택값으로 사용하기 때문입니다.** 검색·marker·저장 목록 중 어느 곳에서 들어와도 같은 ID로 지도 marker, 검색창 제목, 상세 정보를 갱신합니다.

### 구현 7. 검색어를 빠르게 입력하면 서버 요청이 너무 많지 않나요?

**입력이 잠시 멈춘 뒤에만 검색을 시작합니다.** 다만 지연 처리만으로는 늦은 응답을 막을 수 없어서, 요청 순번도 함께 비교해 이전 검색 결과는 화면에 반영하지 않습니다.

### 구현 8. 검색 결과를 계속 내려도 목록을 다시 처음부터 받지 않나요?

**서버가 주는 다음 페이지 cursor를 사용해 필요한 시점에 이어 받아옵니다.** 첫 목록과 다음 목록 요청을 구분하고, 같은 cursor를 동시에 요청하지 않도록 막았습니다.

### 구현 9. 바텀시트는 기본 시트를 사용했나요?

**지도 위에서 높이가 손가락을 따라 변해야 해서 custom sheet로 구현했습니다.** 드래그를 놓으면 닫힘·중간 높이·전체 화면 중 가까운 상태로 한 번만 정리되도록 했고, 전체 화면에서도 같은 시트 흐름을 유지합니다.

### 구현 10. 코스를 선택하면 경로가 화면에 크게 보이는 것은 어떻게 하나요?

**경로를 구성하는 좌표 전체의 범위를 계산해 카메라 영역을 맞춥니다.** 위아래 UI에 가려지는 부분을 고려한 여백을 더해, 경로가 가능한 한 지도 안에 들어오도록 조정합니다.

### 구현 11. 외부 길안내 앱은 어떻게 연결했나요?

**Dynamic Link가 아니라 외부 앱의 URL scheme 또는 카카오내비 SDK가 만든 URL을 `UIApplication.open`으로 실행합니다.** 카카오맵은 `kakaomap://route`에 출발지·경유지·도착지 좌표를 query로 넣고, 카카오내비는 SDK의 `navigateUrl`을 사용합니다. 실행 전 설치 여부와 URL 생성 가능 여부를 확인하고, 실패하면 설치 안내나 다시 시도 가능한 피드백을 보여 줍니다.

### 구현 12. 외부 앱을 보고 다시 돌아온 사실은 어떻게 알 수 있나요?

**앱이 활성 상태로 돌아오는 시점을 감지해 진행 중인 연습 세션을 확인합니다.** 단순히 복귀했다고 완료로 처리하지 않고, 코스·주차장·위치 측정 상태에 맞는 다음 안내만 보여 줍니다.

### 구현 13. 코스 연습 중 위치는 계속 어떻게 확인하나요?

**사용자가 연습을 시작한 세션에서만 위치 업데이트를 받아 현재 위치와 코스 경로의 거리를 계산합니다.** 권한, 위치 정확도, 앱 상태를 함께 확인하며 연습을 종료하거나 세션을 정리하면 위치 측정도 멈춥니다.

### 구현 14. GPS가 코스 위에 있는지는 어떻게 판단하나요?

**현재 위치를 코스 polyline의 가장 가까운 구간에 투영해, 경로에서 150m 이내인 표본만 코스 진입 후보로 인정합니다.** 위치 정확도가 60m를 넘거나 15초보다 오래된 표본은 먼저 버리고, 주행 중에는 이전 표본과 비교해 시간당 45m/s를 넘는 비현실적인 이동도 누적 거리에서 제외합니다. 현재 진행 거리는 통과한 표본 간 실제 이동 거리로 누적합니다.

### 구현 15. 연습 기록은 언제 서버에 저장되나요?

**코스는 위치 기반 인증이 끝난 뒤 연습 생성과 방문 기록 요청이 모두 성공했을 때 저장 완료로 처리합니다.** 둘 중 하나라도 실패하면 완료 화면으로 단정하지 않고 기존 세션을 유지하거나 재시도 흐름을 사용합니다.

### 구현 16. 개발용 앱에서는 왜 더 짧게 테스트할 수 있나요?

**실제 GPS 주행을 매번 재현하기 어렵기 때문에 Dev에만 짧은 외부 앱 체류 테스트 경로를 뒀습니다.** Prod의 위치 인증 정책은 유지하고, Dev에서만 후기 작성·연습기록 화면 연결을 빠르게 확인할 수 있게 했습니다.

### 구현 17. Live Activity에는 어떤 정보를 어떻게 갱신하나요?

**연습 세션의 상태가 바뀔 때 이동 중·주행 중·완료 상태와 진행 정보를 갱신합니다.** 앱을 열지 않아도 잠금 화면이나 Dynamic Island에서 현재 맥락을 볼 수 있게 하되, 완료 저장 전에는 기록 이동 버튼을 노출하지 않습니다.

### 구현 18. Dynamic Island와 잠금 화면 UI를 같은 코드로 만들었나요?

**공통 상태는 같지만, 확장 Dynamic Island는 별도 축소 레이아웃을 사용합니다.** 잠금 화면 카드를 그대로 넣으면 가용 높이를 넘어 잘리기 때문에 긴 코스명은 한 줄로 줄이고 진행 정보만 남겼습니다.

### 구현 19. 앱이 강제 종료된 뒤 Live Activity가 남으면 어떻게 하나요?

**앱을 다시 열거나 Live Activity를 탭했을 때 저장된 세션과 시스템 Activity를 대조합니다.** 맞지 않거나 이어서 인증할 수 없는 오래된 세션은 해당 카드만 정리하고, 다른 완료 카드를 잘못 닫지 않도록 세션 ID를 기준으로 구분합니다.

### 구현 20. Live Activity의 버튼을 누르면 앱에서 어디로 가나요?

**완료된 코스는 연습기록, 완료된 주차장은 홈으로 연결합니다.** 버튼은 기록을 새로 만드는 것이 아니라 이미 완료된 상태를 보기 위한 앱 이동만 담당하고, 탭한 완료 카드는 즉시 정리합니다.

### 구현 21. 후기 수정 화면에 기존 내용은 어떻게 채우나요?

**수정하기를 누르면 후기 상세를 한 번 조회해 선택값과 텍스트를 작성 화면에 넣습니다.** 사용자는 새 화면처럼 보이는 동일한 작성 UI에서 수정하고, 저장 시에는 새 등록이 아닌 수정 요청을 보냅니다.

### 구현 22. 네트워크가 끊겼을 때 화면 전체를 바로 오류로 바꾸지 않는 이유는 무엇인가요?

**짧은 통신 흔들림마다 화면이 바뀌면 사용 경험이 더 불안정해지기 때문입니다.** 먼저 가벼운 재시도 안내를 보여 주고, 연결이 일정 시간 계속 끊긴 홈 지도에서만 별도 대체 화면을 표시합니다.

### 구현 23. 이전 네트워크 응답이 나중 화면을 덮는 문제는 어떻게 막았나요?

**검색·지도·주소 조회마다 현재 요청을 구분하는 번호를 함께 보냅니다.** 응답이 돌아왔을 때 시작 당시 번호가 아직 최신일 때만 화면 값을 바꾸기 때문에, 빠른 이동이나 재검색 뒤에도 이전 결과가 섞이지 않습니다.

### 구현 24. 같은 버튼을 여러 번 누르면 길안내나 저장 요청이 중복되지 않나요?

**진행 중인 요청 상태를 확인해 같은 동작을 다시 시작하지 않도록 막았습니다.** 완료·실패·취소 중 하나로 끝난 뒤에만 다시 시도할 수 있어 외부 앱 실행과 서버 기록이 중복되는 경우를 줄였습니다.

### 구현 25. 앱 업데이트를 꼭 하라는 안내는 어떻게 동작하나요?

**앱 시작 때 App Store의 최신 버전 정보를 확인하고, 현재 설치 버전이 낮으면 기존 업데이트 안내만 표시합니다.** 필요한 업데이트인 경우에는 안내를 닫고 계속 사용하는 흐름을 막아, 이미 수정된 버전으로 이동하도록 합니다.

## 부스 현장 구현 질문

부스에서는 아래 순서로 먼저 답한다. 구조 용어보다 사용자의 입력이 어떤 처리 과정을 거쳐 화면에 반영되는지 설명한다.

### 현장 1. 클러스터링 마커는 어떻게 구현했나요?

**받아온 장소를 주소 앞부분 기준으로 묶은 뒤, 지도 확대 정도에 맞춰 표시 수를 바꿨습니다.** 멀리 볼 때는 시·도 단위 숫자 marker를 보여주고, 확대하면 시·군·구 단위, 마지막에는 실제 코스·주차장 marker로 전환합니다.

### 현장 2. 클러스터가 하나만 남으면 왜 단일 마커로 바뀌나요?

**장소 하나를 보기 위해 cluster를 한 번 더 누르게 하지 않기 위해서입니다.** 묶인 장소가 하나라면 숫자 cluster를 만들지 않고, 처음부터 코스 또는 주차장 아이콘을 바로 보여줍니다.

### 현장 3. 클러스터를 누르면 지도는 어떻게 확대되나요?

**해당 숫자 marker에 포함된 장소들을 다시 찾은 뒤, 다음 단계 marker가 모두 보이는 범위로 지도를 이동시킵니다.** 예를 들어 시·도 cluster를 누르면 그 지역의 시·군·구 marker가 한 화면에 들어오도록 확대합니다.

### 현장 4. 마커가 많을 때 지도 진입이 버벅이지 않나요?

**처음 보이는 marker는 먼저 그리고, 나머지는 짧은 간격으로 나눠 추가합니다.** 초기에는 최대 80개를 표시하고 이후에는 150개씩 약 16ms 간격으로 더해, 대량 장소 데이터가 있어도 지도 첫 화면을 오래 막지 않게 했습니다.

### 현장 5. 검색 결과·마커·상세 시트가 같은 장소를 가리키게 한 방법은 무엇인가요?

**선택한 장소의 ID와 이름을 한곳에 보관하고 모든 진입 경로가 같은 값을 갱신하게 했습니다.** 그래서 검색 결과를 누르든 marker를 누르든 저장 목록에서 오든, 활성 marker·검색창 제목·상세 시트가 같은 장소를 보여줍니다.

### 현장 6. 지도 이동 중 이전 장소 목록 응답이 늦게 오면 어떻게 하나요?

**지도 이동마다 요청 순번을 올리고, 마지막 순번의 응답만 사용합니다.** 사용자가 강릉에서 서울로 빠르게 이동했을 때 강릉 목록 응답이 늦게 도착해도 서울 목록을 덮지 못하게 했습니다.

### 현장 7. 검색 debounce만으로 중복·역순 응답을 막을 수 있나요?

**아닙니다. 입력 지연 처리와 응답 순서 제어는 별개입니다.** 입력을 잠시 기다린 뒤 요청 수를 줄이고, 각 요청 번호를 비교해 이미 시작된 이전 검색 요청은 최신 결과에 반영하지 않습니다.

### 현장 8. 지역 검색과 장소 검색은 어떻게 다르게 처리하나요?

**지역 결과는 지도 이동용, 장소 결과는 상세 열기용으로 따로 처리합니다.** 예를 들어 `서울 중구`를 누르면 그 지역 중심으로 지도를 옮겨 목록을 새로 불러오고, 특정 주차장을 누르면 해당 주차장 상세를 엽니다.

### 현장 9. 코스 등록 중 핀을 움직일 때 주소가 깜빡이지 않는 이유는 무엇인가요?

**핀 이동 중에는 기존 주소를 유지하고, 새 주소 조회가 성공했을 때만 교체합니다.** 화면 중앙 핀 아래 주소와 사용자가 확정한 출발지·경유지·도착지를 별도로 보관해 이동 중 등록 내용이 임의로 바뀌지 않습니다.

### 현장 10. 외부 길안내 앱이 없거나 실행에 실패하면 어떻게 하나요?

**길안내를 열기 전에 설치 여부와 목적지 준비 상태를 확인하고, 실패하면 설치 안내 또는 오류 메시지를 보여줍니다.** 코스와 주차장은 완료 판정만 다르게 두고, 앱 선택·URL 실행·연속 탭 방지는 공통 처리로 재사용했습니다.

### 현장 11. 코스 연습 완료를 단순히 버튼 탭으로 처리하지 않는 이유는 무엇인가요?

**버튼을 눌렀다는 사실만으로는 실제 주행을 판단할 수 없기 때문입니다.** 사용자가 시작한 연습에서 위치가 코스와 맞는지 확인한 뒤, 연습 생성과 방문 기록 API가 모두 성공한 경우에만 완료 기록과 후기 작성 흐름을 엽니다.

### 현장 12. 앱이 백그라운드 또는 강제 종료되면 Live Activity는 어떻게 관리하나요?

**진행 중인 연습 정보를 기기에 보관하고, 앱을 다시 열 때 Live Activity와 서로 맞는지 확인합니다.** 강제 종료 뒤에는 GPS 흐름이 끊겼다고 보고 자동 인증을 이어가지 않으며, 남아 있는 잘못된 카드는 앱 재진입이나 카드 탭 시 정리합니다.

### 현장 13. 위치 권한이나 GPS가 끊겼을 때 사용자를 계속 방해하지 않나요?

**마지막으로 확인된 위치를 유지하고, 짧은 GPS 단절마다 알림을 반복하지 않습니다.** 사용자가 직접 위치 버튼을 누르거나 일정 시간 이상 계속 실패한 경우에만 위치 확인 안내를 보여줍니다.

### 현장 14. 후기 수정은 왜 새 화면을 만들지 않고 기존 작성 화면을 재사용했나요?

**작성 화면을 하나만 유지해 입력 규칙과 UI가 달라지는 것을 막았습니다.** 수정하기를 누르면 상세 API로 기존 점수·선택값·텍스트를 가져와 입력칸에 채우고, 저장할 때만 새 후기 등록 대신 수정 API를 호출합니다.

### 현장 15. 네트워크 오류와 검색 결과 없음을 어떻게 구분하나요?

**서버가 정상적으로 빈 목록을 준 경우와 통신이 실패한 경우를 다르게 보입니다.** 전자는 `추천할 수 있는 연습 코스가 없어요` 같은 빈 화면을, 후자는 네트워크 확인과 다시 시도 버튼을 보여줍니다.

## 1. 레이어드 아키텍처와 의존성 방향

### 1. 왜 App·Core·Data·Domain·Presentation 레이어로 나눴나요?

**각 레이어가 바뀌는 이유를 분리하기 위해 나눴습니다.** Domain은 제품 계약, Data는 서버·저장소 변환, Presentation은 화면 상태, App은 조립을 맡아 API나 SDK 변경이 화면 전반으로 번지는 것을 줄였습니다.

### 2. Domain을 Data와 Presentation에서 독립시킨 이유는 무엇인가요?

**제품 개념이 서버 DTO나 SwiftUI 표현에 종속되지 않게 하기 위해서입니다.** Domain에는 Entity와 Repository protocol만 두고, Alamofire·SwiftUI·Kakao SDK·DTO import가 들어가지 않도록 검토했습니다.

### 3. Repository protocol을 Domain에 두는 이유는 무엇인가요?

**Feature가 데이터 구현이 아니라 제품 계약에 의존하도록 하기 위해서입니다.** Presentation은 `PlaceRepository`, `ReviewRepository` 같은 계약만 알고, Data의 RepositoryImpl이 실제 API·DTO·Mapper를 담당합니다.

### 4. `AppDependencies`는 왜 필요한가요?

**구현체 조립을 한곳으로 모으기 위해 필요합니다.** token store, 네트워크, remote data source, repository, 공유 runtime service를 App에서 조립하고 View나 Reducer가 구현체를 직접 생성하지 않게 했습니다.

### 5. Core에 제품 Feature 코드를 두지 않는 이유는 무엇인가요?

**공통 기반이 특정 제품 정책을 알기 시작하면 변경 비용이 커지기 때문입니다.** 실제 두 Feature 이상이 공유하거나 전역 기술 경계인 경우만 Core 후보로 두고, 레벨 이미지·약관 모델·분석 이벤트 catalog처럼 제품 성격이 강한 코드는 Presentation 또는 App으로 이동했습니다.

## 2. MVI·Reducer·child Delegate

### 6. 왜 MVI 형태의 상태 관리를 사용했나요?

**지도·검색·바텀시트·후기·위치처럼 비동기 상태가 많은 앱에 상태 전이 추적이 필요했기 때문입니다.** View는 Action을 보내고, Reducer가 State 변경과 Effect 시작·취소를 결정하며 Store가 Main Actor에서 이를 조정합니다.

### 7. View에서 직접 API를 호출하지 않는 이유는 무엇인가요?

**View lifecycle과 재렌더링이 요청의 소유자가 되면 중복 요청과 이탈 후 반영을 통제하기 어렵기 때문입니다.** 제품 비동기 작업은 Reducer Effect 또는 lifetime이 명확한 Service에서 시작하고, View는 렌더링과 Action 전달만 담당합니다.

### 8. parent와 child reducer는 어떻게 통신하나요?

**child는 typed Delegate로 결과와 의도만 내보내고 parent가 sibling 전환을 중재합니다.** child가 다른 child State를 직접 읽거나 수정하지 않게 해서 Home의 Map·Search·BottomSheet와 Review·DrivePractice 사이의 결합을 낮췄습니다.

### 9. reducer가 커지면 무조건 파일을 나누나요?

**아닙니다. 줄 수가 아니라 독립 State·Action·Effect·취소 정책이 있는지로 판단합니다.** 예를 들어 지도나 검색처럼 자체 비동기 생명주기가 있는 책임은 child reducer로 분리하고, 단순 UI 블록은 private extension이나 가까운 SubView로 유지합니다.

### 10. 화면 전환 중 child effect가 남는 문제는 어떻게 다루나요?

**route를 바꾸기 전에 child의 reset 또는 deactivate Action을 거치게 합니다.** 상세 조회·제출·역지오코딩처럼 화면 수명에 묶인 작업은 cancellation ID와 revision 검증을 함께 사용해 늦은 응답이 새 화면을 덮지 못하게 합니다.

## 3. Swift Concurrency·최신성·취소

### 11. `@MainActor`는 어떤 기준으로 적용했나요?

**UI State, Store·Reducer 조정, main-thread SDK 경계에만 적용했습니다.** 단순 컴파일 오류를 없애기 위해 붙이지 않고, 실제 UI 또는 SDK가 Main Actor를 요구하는지 먼저 확인했습니다.

### 12. `Task`를 만들면 자동으로 백그라운드에서 실행되나요?

**아닙니다. `Task` 자체는 실행 actor를 보장하지 않으므로 UI State와 SDK 경계를 분리해서 봐야 합니다.** CPU 작업을 무리하게 detached로 보내기보다, Reducer Effect의 구조화된 수명과 `await` 뒤 최신성 검증을 우선했습니다.

### 13. `Task.detached`를 왜 거의 사용하지 않았나요?

**취소·우선순위·Sendable·actor context가 부모 작업과 끊기기 때문입니다.** 독립 lifetime이 제품 요구사항으로 명확한 경우가 아니라면, 기존 Store/Reducer Effect의 취소 관리 안에서 작업하도록 했습니다.

### 14. stale response는 어떻게 막나요?

**요청 revision과 현재 선택 대상·route를 함께 비교해 막습니다.** 검색어 변경, 지도 중심 이동, 주소 선택 대상 변경 뒤에 이전 응답이 와도 현재 State와 맞지 않으면 무시합니다.

### 15. Snackbar가 연속 표시될 때 이전 타이머가 새 메시지를 닫지 않나요?

**취소된 Task는 sleep 이후 dismiss Action을 보내지 않게 처리했습니다.** 최신 Snackbar만 닫히도록 cancellation 확인과 메시지 revision을 사용해 타이머 경쟁을 줄였습니다.

## 4. API·DTO·Mapper·Repository

### 16. DTO를 Presentation까지 전달하지 않는 이유는 무엇인가요?

**서버의 optional·raw value·날짜 형식이 화면 모델을 오염시키지 않게 하기 위해서입니다.** Data Mapper가 DTO를 Domain Entity로 변환하고, Presentation은 사용자에게 필요한 제품 모델만 사용합니다.

### 17. API 응답의 `isSuccess`, `data`, 빈 응답은 어디서 처리하나요?

**RemoteDataSource의 공통 응답 helper에서 검증합니다.** RepositoryImpl은 Domain 입력 조립과 Mapper 호출에 집중하고, 성공 payload·empty response·API error 정책을 각 Feature가 중복 구현하지 않게 했습니다.

### 18. 서버 DTO 변경을 발견하면 어떤 순서로 대응하나요?

**Swagger endpoint·환경·wrapper를 먼저 확인한 뒤 DTO, Mapper, Domain contract, 호출부 순서로 좁힙니다.** 화면에서 임시 보정하지 않고 Data 변환 경계에서 처리하며, 같은 변경 단위에 API 가이드의 검증 기록과 필요한 TODO를 갱신합니다.

### 19. nullable 값이나 알 수 없는 enum은 어떻게 처리하나요?

**Mapper에서 제품 모델로 안전하게 변환 가능한지 명확히 판단합니다.** 필수값 누락·알 수 없는 enum·안전하지 않은 숫자 변환은 `NetworkError.decodingFail`로 분류해 잘못된 화면 상태를 만들지 않습니다.

### 20. 날짜 파싱을 공통화한 이유는 무엇인가요?

**서버가 허용하는 ISO-8601 형식 차이를 Feature별로 다르게 해석하지 않게 하기 위해서입니다.** fractional seconds와 timezone 없는 서버 포맷을 Data 전용 parser에 모아 Member·Practice·Review 변환이 같은 기준을 쓰게 했습니다.

## 5. 검색·지도·마커·바텀시트

### 21. 검색 debounce만으로 이전 결과 문제를 막을 수 있나요?

**아닙니다. debounce는 요청 수를 줄일 뿐, 이미 시작된 요청의 순서를 보장하지 않습니다.** 그래서 검색 reducer가 request ID를 소유하고 최신 요청의 결과만 State에 반영합니다.

### 22. 행정구역 선택과 장소 선택을 왜 구분하나요?

**행정구역은 지도 viewport 이동, 장소는 상세 선택이라는 서로 다른 의도이기 때문입니다.** 지역 선택은 중심 좌표로 카메라를 옮기고 목록을 다시 조회하며, 장소 선택은 선택 마커·검색창 제목·상세 바텀시트를 같은 선택 상태로 동기화합니다.

### 23. 선택 마커와 검색창·상세 시트 상태가 어긋나는 문제는 어떻게 막나요?

**선택 경로가 달라도 최종적으로 하나의 Home 선택 상태를 갱신하도록 했습니다.** 검색·마커·저장 목록 진입에서 선택한 place ID와 이름을 공유해 활성 마커, 검색창 뒤로가기, 상세 시트가 같은 대상을 표현합니다.

### 24. 클러스터가 한 개일 때 단일 마커처럼 처리한 이유는 무엇인가요?

**한 번 더 탭해야 장소 종류를 알 수 있는 불필요한 단계를 줄이기 위해서입니다.** 클러스터 count가 1이면 zoom level과 관계없이 코스·주차장 단일 마커 렌더링 규칙을 적용했습니다.

### 25. custom bottom sheet에서 drag 상태를 Reducer에 모두 넣지 않은 이유는 무엇인가요?

**손가락 이동값은 View-local 표현 상태이고 제품 상태가 아니기 때문입니다.** drag translation과 연속 높이는 View에서 처리하고, 놓은 뒤의 route·확장 여부·상세 전환처럼 제품 의미가 생기는 결과만 Reducer에 전달합니다.

## 6. CoreLocation·백그라운드 측정·경로 매칭

### 26. 위치 측정은 언제 시작하나요?

**사용자가 `연습하러 가기`를 선택한 활성 세션에서만 시작합니다.** 홈 지도 탐색과 실제 연습 측정을 분리하고, 세션 종료·로그아웃·정합성 실패 시 위치 업데이트를 중단합니다.

### 27. 코스 완료를 버튼 탭만으로 처리하지 않는 이유는 무엇인가요?

**실제 코스 경험과 무관한 연습기록·후기 작성이 늘어날 수 있기 때문입니다.** 코스는 경로 매칭과 인증 조건을 통과하고 `register → recordVisit`이 성공한 뒤에만 인증 완료로 처리합니다.

### 28. 주차장과 코스의 완료 기준은 왜 다른가요?

**코스는 경로 진행, 주차장은 특정 장소 도착이라는 제품 모델이 다르기 때문입니다.** 코스는 route matching을 사용하고, 주차장은 장소 반경 진입을 기준으로 관리하며 후기 정책도 분리합니다.

### 29. GPS가 끊기면 매번 오류를 보여주나요?

**아닙니다. 마지막 유효 위치를 유지하고 사용자 행동 또는 장시간 연속 실패가 있을 때만 안내합니다.** 지하철처럼 일시적인 위치 단절에서 Snackbar가 반복되는 피로를 줄이기 위한 정책입니다.

### 30. 위치·경로 매칭 성능은 어떻게 판단했나요?

**정적 복잡도만 보고 최적화하지 않고 metric test와 실기기 계측을 분리했습니다.** 긴 route와 다수 marker 상황은 Simulator에서 기준을 확인하고, 실제 hitch·메모리 판단은 Time Profiler와 SwiftUI Instruments 실기기 검증을 남겨뒀습니다.

## 7. Live Activity·앱 lifecycle·Dynamic Island

### 31. Live Activity를 앱 내부 상태와 어떻게 동기화하나요?

**DrivePractice session을 원본으로 두고 runtime service가 start·sync·end만 수행합니다.** Activity UI와 공유 Attributes는 extension target에 두고, 앱 전용 위치·세션 정책이 Widget에 섞이지 않도록 분리했습니다.

### 32. Live Activity 업데이트를 자주 보내지 않는 이유는 무엇인가요?

**빈번한 업데이트는 배터리·시스템 제약·사용자 체감 측면에서 비용이 있기 때문입니다.** 현재는 단계 변경, 일정 시간 경과, 진행률 의미 있는 변화 같은 기준으로 업데이트 빈도를 제한합니다.

### 33. 앱 강제 종료 뒤 남은 Live Activity는 어떻게 처리하나요?

**다음 앱 진입 또는 Activity 탭 시 저장 세션과 시스템 Activity를 대조해 고아 카드를 정리합니다.** 종료된 프로세스는 즉시 코드를 실행할 수 없다는 iOS 제약을 인정하고, 잘못된 세션을 재개하거나 방문 기록을 만들지 않도록 합니다.

### 34. 주행 중 강제 종료 후 자동 재개하지 않는 이유는 무엇인가요?

**GPS 연속성이 끊긴 뒤에는 신뢰 가능한 주행 인증을 보장할 수 없기 때문입니다.** 세션을 중단 처리하고 인증·후기·방문 기록으로 잘못 이어지지 않게 하는 것이 더 안전합니다.

### 35. Dynamic Island 확장 화면이 잘린 문제는 왜 생겼고 어떻게 고쳤나요?

**잠금 화면용 큰 카드 레이아웃을 확장 Island에 그대로 넣은 것이 원인이었습니다.** 확장 상태는 상태별 짧은 텍스트와 얇은 진행 바로 별도 구성하고, 긴 코스명은 한 줄 말줄임 처리해 가용 영역을 넘지 않게 했습니다.

## 8. 로그인·보안·개인정보

### 36. access token과 refresh token은 어떻게 보호하나요?

**로그인 세션 토큰은 Keychain 기반 저장소로 관리합니다.** 토큰 원문은 로그·Analytics·UI·커밋에 노출하지 않고, 인증 실패는 네트워크 오류 흐름과 분리해 처리합니다.

### 37. Kakao key를 앱에 넣어도 안전한가요?

**native app key는 앱 번들에 들어가므로 서버 비밀처럼 취급할 수는 없습니다.** 대신 Kakao console에서 bundle ID·플랫폼 제한을 적용하고, 저장소와 로그에는 남기지 않으며 local xcconfig로 주입합니다.

### 38. 위치·검색·분석 데이터의 개인정보 원칙은 무엇인가요?

**원문 검색어, 정밀 좌표, GPS 경로, 토큰, 회원 식별값을 분석 event와 release log에 넣지 않는 것이 원칙입니다.** Analytics는 low-cardinality 범주값과 성공 결과 중심으로 보내고, 지도·입력·인증 화면은 관측 도구에서 마스킹 대상으로 관리합니다.

### 39. 로그아웃·탈퇴에서 활성 연습 세션을 정리하는 이유는 무엇인가요?

**다른 계정으로 위치 측정 상태나 Live Activity가 이어지는 것을 막기 위해서입니다.** 저장된 측정 payload와 활성 Activity를 함께 정리해 계정 경계를 유지합니다.

### 40. 오류 로그에는 무엇을 남기나요?

**endpoint category, HTTP status family, 안전한 오류 종류 같은 진단 정보만 남깁니다.** 정확한 좌표, 토큰, 원문 서버 응답, 닉네임처럼 민감하거나 식별 가능한 값은 제외합니다.

## 9. Dev·Prod·배포·관측

### 41. Dev와 Prod를 왜 분리했나요?

**테스트 편의 기능이 실제 사용자 정책에 섞이지 않게 하기 위해서입니다.** scheme과 xcconfig로 bundle ID, 표시명, icon, 환경 flag, 업데이트 검사, 배포 대상을 분리합니다.

### 42. Dev와 Prod가 같은 API endpoint를 쓰는 문제는 없나요?

**현재는 같은 운영 endpoint를 사용하므로 테스트 계정과 서버 상태를 더 엄격히 분리해야 합니다.** 특히 탈퇴·복구처럼 장기 상태를 남기는 검증은 운영 사용자 계정으로 하지 않는 정책을 둡니다.

### 43. 강제 업데이트는 어떤 실패 정책을 갖나요?

**최신 버전 확인에 실패하거나 제한 시간 안에 끝나지 않으면 앱을 막지 않습니다.** 네트워크 오류 때문에 사용자가 앱에 진입하지 못하는 상황을 피하면서, 최신 버전이 확인된 경우에만 기존 강제 업데이트 dialog를 표시합니다.

### 44. Fastlane 배포 시 build number는 어떻게 관리하나요?

**`prod_beta`와 `dev_beta` lane이 App Store Connect의 다음 build number를 계산해 archive에 주입합니다.** 프로젝트 파일의 build number를 매번 수정하지 않아 브랜치·배포 작업의 충돌을 줄였습니다.

### 45. Firebase·Crashlytics·Clarity는 어떻게 역할을 나눴나요?

**Firebase는 이벤트·크래시·성능, Clarity는 화면 상호작용 관측에 사용합니다.** SDK 전송 adapter는 Core에 두고, 제품 event catalog는 Presentation Shared에 둬 전송 기술과 제품 행동 정의를 분리했습니다.

## 10. 테스트·QA·기술 부채

### 46. build 성공만으로 기능 검증이 충분한가요?

**충분하지 않습니다. build는 컴파일·링크 확인일 뿐, 상태 전이와 외부 SDK 흐름을 보장하지 않습니다.** 그래서 XCTest, `git diff --check`, 정적 검색, 수동 QA, 실기기 검증을 분리해 기록합니다.

### 47. 어떤 회귀를 XCTest로 보호하고 있나요?

**stale response와 제품 정책처럼 재현 가능한 상태 전이를 우선 보호합니다.** 검색 이전 요청 무시, 역지오코딩 최신 주소 반영, 코스·주차장 후기 가능 상태 구분, 연습 유형 선택 보존 같은 reducer·service 시나리오를 테스트합니다.

### 48. 왜 Live Activity와 GPS를 Simulator만으로 최종 검증하지 않나요?

**백그라운드 위치, 권한 정확도, 외부 앱 전환, ActivityKit 수명주기는 실제 기기와 시스템 정책의 영향을 크게 받기 때문입니다.** Simulator는 UI·상태 전환·기본 컴파일 확인에 쓰고, 최종 릴리스 판정은 실기기 시나리오로 분리합니다.

### 49. 현재 남아 있는 기술 부채는 무엇인가요?

**위치·Live Activity·Kakao 외부 앱 전환의 장시간 실기기 검증과 대규모 marker 성능 계측이 남아 있습니다.** 코드리뷰에서 정적 구조 문제는 정리했지만, 실제 기기에서 재현된 hitch·메모리 근거가 생길 때만 추가 최적화를 진행하는 방침입니다.

### 50. 평가자가 "가장 어려웠던 기술 문제"를 물으면 무엇을 답하나요?

**외부 내비게이션으로 앱이 이탈한 뒤에도 신뢰할 수 있는 연습 세션을 유지하면서, 잘못된 기록·후기·Live Activity 고아 상태를 막는 문제였다고 답하겠습니다.** 위치 측정 session, 앱 lifecycle, 서버 방문 기록, ActivityKit 상태를 분리하고 request ID·취소·복구 정책을 연결했으며, 실제 기기 QA가 필요한 한계도 함께 관리하고 있다고 설명하겠습니다.

## 서비스 구현 상세 후속 질문·답변

### 51. 클러스터링 마커는 어떤 방식으로 처리했나요?

**서버에서 받은 장소 목록을 주소 단위로 묶고, 지도 zoom level에 따라 표시 단계를 바꿨습니다.** 낮은 zoom은 시·도, 중간 zoom은 시·군·구 기준으로 grouping하고, 높은 zoom에서는 개별 코스·주차장 마커를 렌더링합니다.

### 52. 클러스터가 한 개의 장소만 포함하면 왜 단일 마커로 표시하나요?

**사용자가 한 번 더 탭해서 장소 종류를 확인하는 단계를 없애기 위해서입니다.** cluster 생성 전 member count를 확인해 1개면 cluster가 아닌 원래 코스·주차장 마커를 반환합니다.

### 53. 클러스터 위치는 어떻게 정하나요?

**같은 cluster member들의 위도·경도 평균을 사용합니다.** 임의의 첫 장소 좌표를 쓰면 지역 묶음의 중심에서 크게 벗어날 수 있어, 현재는 member coordinate의 평균으로 표시 위치를 만들었습니다.

### 54. 클러스터를 탭하면 어떤 일이 일어나나요?

**현재 cluster의 다음 zoom tier가 모두 들어오도록 카메라를 이동시킵니다.** marker ID에 tier와 지역 key를 포함하고, 같은 지역 member를 다시 계산해 다음 단계 marker 좌표 집합을 focus target으로 전달합니다.

### 55. 마커가 많을 때 한 번에 그리지 않는 이유는 무엇인가요?

**초기 지도 진입의 main-thread 부담을 줄이기 위해 progressive rendering을 적용했습니다.** 첫 batch를 먼저 그리고 이후 marker를 16ms 간격 batch로 추가해, 모든 prefix snapshot을 미리 만들지 않으면서도 사용자에게 빠른 첫 화면을 제공합니다.

### 56. 선택된 마커는 어떻게 유지하나요?

**선택 ID를 Home Map State의 단일 원본으로 둡니다.** 검색 결과, 지도 마커, 저장 목록처럼 진입 경로가 달라도 place ID와 선택 이름을 같은 상태에 반영해 활성 마커·검색창·상세 시트가 동기화됩니다.

### 57. 지도 viewport가 바뀔 때 장소 목록 API가 여러 번 호출되지 않나요?

**viewport와 request revision을 함께 관리해 최신 목록 요청만 반영합니다.** camera event가 연속으로 들어와도 이전 viewport 결과는 무시하고, 수동 재검색·지역 이동·초기 조회의 목적을 별도로 구분합니다.

### 58. 추천 목록 cursor pagination은 중복 item을 어떻게 막나요?

**append 전에 기존 item ID 집합으로 중복을 제거합니다.** cursor 요청이 중복되거나 API 응답이 경계 item을 다시 포함해도 목록에 같은 장소가 두 번 표시되지 않습니다.

### 59. 비로그인 사용자는 지도 목록을 볼 수 있나요?

**볼 수 있는 공개 목록과 회원 상태가 필요한 동작을 분리합니다.** 장소 목록 요청은 active session 여부에 따라 public/member access를 선택하고, 단일 코스·주차장 선택처럼 인증이 필요한 흐름은 지도 이동 전에 로그인 의도만 올립니다.

### 60. 필터 선택값은 왜 화면을 닫아도 유지되나요?

**사용자가 반복해서 같은 조건을 설정하지 않게 하기 위해 selection을 별도 store에 저장합니다.** filter sheet에서는 draft와 applied selection을 구분해 적용 전 취소와 적용 후 목록 재조회가 섞이지 않게 합니다.

### 61. 카테고리 전환 뒤 이전 연습유형 선택을 보존한 이유는 무엇인가요?

**카테고리별 다중 조건 선택이 가능한 필터와 단일 표시 카테고리를 분리하기 위해서입니다.** Home 필터는 선택한 유형을 누적하고, 현재 펼친 카테고리만 유형 영역을 보여주며, 코스 등록은 한 카테고리만 표시하되 이전 유형 선택값은 보존합니다.

### 62. 지역 검색과 장소 검색은 왜 같은 결과 화면에 섞어 두나요?

**사용자가 입력한 한 검색어로 지도 이동과 상세 선택을 모두 할 수 있어야 하기 때문입니다.** 다만 지역 row 탭은 지도 중심 이동·viewport 재조회로, 장소 row 탭은 place 상세 선택으로 각기 다른 Action을 보냅니다.

### 63. `서울특별시`를 `서울`로 보이는 방식으로 바꾼 것은 서버 데이터를 수정한 것인가요?

**아닙니다. 표시 전용 formatter로 특별시·광역시 표기만 축약합니다.** 서버 원문과 최근 검색 저장값은 보존해 검색 의미나 좌표 선택이 UI 표현 때문에 변하지 않게 했습니다.

### 64. 검색 결과 없음과 네트워크 오류를 어떻게 구분하나요?

**성공 응답의 빈 `items` 배열은 empty state, 요청 실패는 retry state로 분리합니다.** 둘을 같은 문구로 처리하면 사용자가 데이터가 없는지 인터넷이 끊겼는지 판단할 수 없기 때문입니다.

### 65. 장소 상세를 선택한 뒤 지역 검색하면 이전 상세 시트가 남는 문제는 어떻게 막았나요?

**상세 child effect를 teardown한 뒤 추천 목록 route로 전환합니다.** 코스·주차장 상세의 늦은 응답이 새 지역 목록을 덮지 않도록 reset, effect cancellation, request revision을 순서대로 적용합니다.

### 66. 코스 polyline은 왜 별도 overlay 상태로 관리하나요?

**마커 목록과 경로 선은 갱신 주기와 선택 조건이 다르기 때문입니다.** 선택 코스의 경로는 route overlay로 렌더링하고, marker 갱신 중에는 필요 없는 polyline을 다시 만들지 않도록 분리했습니다.

### 67. polyline에 외곽선을 적용한 방식은 무엇인가요?

**Kakao Map의 `PerLevelPolylineStyle`에서 본선과 stroke를 함께 지정해 가시성을 확보했습니다.** 현재 본선은 12pt, 외곽 stroke는 2pt이며 외곽 색상은 `RodiColor.primary800`의 `#2600B1`로 통일했습니다.

### 68. 코스 등록에서 중앙 핀 주소가 바뀔 때 입력값이 깜빡이지 않게 한 방법은 무엇인가요?

**reverse geocoding 요청 시작 시 기존 candidate 주소를 비우지 않습니다.** 최신 요청이 성공한 시점에만 주소를 교체하고, 출발지·경유지·도착지의 확정 데이터는 선택 버튼을 누르기 전까지 따로 유지합니다.

### 69. 코스 등록에서 출발지·도착지·경유지 확정 상태를 왜 분리했나요?

**지도 중앙의 임시 주소와 실제 등록 payload를 구분해야 잘못된 경로 등록을 막을 수 있기 때문입니다.** candidate 주소가 준비돼야 선택 버튼을 활성화하고, 출발지 확정 후 도착지 단계로 전환하며, 경로 조회 완료 전에는 최종 완료를 허용하지 않습니다.

### 70. 경유지를 삭제했을 때 polyline이 사라지는 문제는 어떻게 접근했나요?

**입력 행 배열만 수정하지 않고 route 계산 상태와 선택 중인 주소 요청을 함께 정리해야 합니다.** 삭제 대상이 현재 선택 target이면 관련 주소 요청을 취소하고, 남은 waypoint 기준으로 route 상태를 다시 계산하게 합니다.

### 71. 코스 등록 장소 검색은 서버 API와 같은 계층을 쓰나요?

**RODI backend API와 Kakao Local API는 성격이 달라 분리합니다.** 백엔드 DTO는 Data Layer를 거치고, Kakao Local은 Feature 전용 외부 API adapter로 CourseRegistration Service 안에 한정해 Domain에 SDK·외부 DTO가 새지 않게 했습니다.

### 72. 외부 길안내 앱이 설치되지 않은 경우는 어떻게 처리하나요?

**설치 여부를 먼저 확인하고 설치 페이지 또는 오류 feedback으로 분기합니다.** RouteGuidance child reducer가 앱 선택, 설치 안내, URL 실행, 연속 탭 방지, 실패 결과를 공통으로 소유합니다.

### 73. 길안내 앱 선택을 기억하는 이유와 범위는 무엇인가요?

**반복 연습에서 같은 선택을 다시 묻지 않기 위한 화면 편의 설정입니다.** 선택 앱만 저장하고, 실제 URL 실행 전에는 설치 여부와 현재 위치·목적지 준비 상태를 다시 확인합니다.

### 74. 후기 수정 화면에 기존 값은 어떻게 채우나요?

**수정 진입 시 후기 상세 조회 결과를 `ReviewDraft`로 변환해 기존 작성 화면에 주입합니다.** 신규 작성과 수정은 같은 form UI를 재사용하되, 저장 요청만 POST와 PUT으로 분기합니다.

### 75. 레벨별 후기에서 선택 레벨에 후기만 없으면 왜 드롭다운을 유지하나요?

**장소 전체 후기가 존재한다면 사용자는 다른 레벨을 즉시 다시 선택할 수 있어야 하기 때문입니다.** 전체 후기 수와 선택 레벨 첫 페이지 item을 분리해 판단하고, 선택 레벨 0건에는 드롭다운·전체보기·후기 CTA를 유지합니다.

### 76. 신고·차단 이후 목록을 즉시 갱신하는 이유는 무엇인가요?

**사용자가 방금 처리한 콘텐츠를 같은 세션에서 다시 보지 않게 하기 위해서입니다.** 해당 Review child flow의 결과를 상위 reducer에 Delegate로 전달해 cache·목록 상태를 갱신하고, 서버 재조회 전에도 UI 정합성을 유지합니다.

### 77. 후기 작성 후 내 게시글·연습기록이 최신화되는 흐름은 어떻게 설계했나요?

**완료 결과를 전역 callback으로 흩뿌리지 않고 typed refresh request로 중계합니다.** 작성·수정의 진입 출처를 보관하고, 완료 후 필요한 Home·My child에 refresh ID를 전달해 각 화면이 자신의 GET을 다시 실행하게 합니다.

### 78. 네트워크 재시도 버튼을 공통화한 이유는 무엇인가요?

**오류 문구와 hit target, loading 상태가 화면마다 달라지는 것을 줄이기 위해서입니다.** `RodiRetryButton`으로 primary 채움·흰색 body2·내부 여백·radius를 통일하고, 각 Feature는 자신의 reload Action만 전달합니다.

### 79. 강제 업데이트 검사는 왜 Root 진입 전에 처리하나요?

**최신 버전이 필수인 경우 하위 화면이 잠깐 보였다가 막히는 전환을 피하기 위해서입니다.** Prod는 Store 버전 확인 결과가 올 때까지 route를 보류하고, 실패·timeout은 네트워크 문제로 앱 전체를 차단하지 않도록 fallback합니다.

### 80. 서비스 구현 설명에서 가장 강조할 만한 트레이드오프는 무엇인가요?

**정확성, 사용자 피로도, 시스템 제약 사이의 균형을 상태별로 선택했다는 점입니다.** 예를 들어 GPS 실패는 매번 알리지 않고, Live Activity는 빈번히 갱신하지 않으며, 인증이 불충분한 코스는 기록·후기 처리로 성급하게 이어지지 않도록 했습니다.

## 검증 범위

- 문서의 아키텍처·배포·코드리뷰 설명은 현재 활성 문서와 코드 경로를 대조해 작성했다.
- GPS, 백그라운드 위치, Kakao 외부 앱 전환, Live Activity lifecycle은 실기기 수동 QA가 최종 기준이다.
- 이 문서는 실제 구현의 원본이 아니며, 구현 변경 시에는 live code와 해당 Architecture·API·Release 문서를 우선한다.
